Open issues

One documented issue is open in v1.0.2. It is a distribution problem rather than a defect in the file engine, and it does not put your data at risk. It is listed here in full because it is the first thing a new user meets, and meeting an unexplained blue screen is how people abandon good software.

SmartScreen blocks the installer: "Windows protected your PC"

Open

What you see

After launching Desktop-Organizer-Setup-v1.0.2.exe a blue dialog covers the window, stating that Windows has prevented the app from running because it is not commonly downloaded or is from an unknown publisher. Depending on your build of Windows and your antivirus policy you may also see a Defender prompt offering to remove the file, and browsers may mark the download as unusual.

Reason

The installer is not code-signed. Code signing needs a purchased certificate bound to a verified identity, and this is an unfunded MIT project that does not hold one. SmartScreen also weighs reputation, which accumulates only as the same unmodified asset is downloaded more often, so a recently published 108.7 MB build from a small repository starts with none. Both effects are cumulative and neither indicates tampering.

Solution

In the dialog, click More info and then Run anyway. That is the supported path, and it is safe once you have verified the file. The real fix is purchasing a code-signing certificate and signing every build, which this unfunded project has not done; that is why the entry stays open rather than closed.

Before you click anything

Confirm you have the released asset and not a lookalike. Download only from the releases page, then compute the digest of the file you have and compare it with the published asset: certutil -hashfile "Desktop-Organizer-Setup-v1.0.2.exe" SHA256 run in the folder holding the installer prints the hash, and the v1.0.2 release page carries the official file. If the name, size or source looks wrong, delete the copy and start again from GitHub.

Workarounds

  • Right-click the installer, open Properties, tick Unblock at the bottom of the General tab, apply, then run it. This clears the mark Windows puts on files downloaded from another machine.
  • Keep a verified copy of the setup file somewhere you trust, so a re-run does not need another download.
  • If endpoint protection managed by your organisation blocks the file outright, have an administrator allow-list the verified hash rather than work around the policy yourself; unsigned utilities are commonly stopped by rule, not by judgement.
  • Never disable SmartScreen or antivirus globally to get an installation through. Use the targeted steps above instead.

Status

Open and accepted. Reputation improves as downloads of the unchanged asset accumulate, and signing remains a funding decision. Watch the issue tracker for a change; the download page repeats the same guidance so that nobody has to find this page the hard way.

Verification is not the same as trust

A matching hash proves the file is the one published for v1.0.2. It does not prove the code is sound. For that, read the source at the repository, which is where the privacy claims on this site are either true or not.

How this page is maintained

An entry belongs here when a user can meet it in the released build and the workaround is not obvious from the interface. Once a fix ships, the item moves into the resolved list under its release, so that people still on an older version can check themselves rather than re-report it. Defects found in the code that nobody can trigger from the interface, and anything tied to one unusual machine configuration, stay in the GitHub tracker instead: this page is for conditions you can run into, not a second changelog.

  • Open — reproducible in v1.0.2, with a workaround and no fix available yet.
  • Resolved — fixed in a named release; updating clears it.
  • By design — expected behaviour, listed under Being watched so that it stops being filed as a fault.

Resolved in v1.0.2

Seven defects were closed in this release. If you are on an older build and one of these describes your experience, updating is the fix; if you are already on v1.0.2 and you can reproduce any of them, that is a new report and we want it.

  • Download organisation timing. Files still in transit could be filed before the browser finished writing them. v1.0.2 respects the stabilization and completion delays, and never touches in-progress extensions.
  • Notification spam. Repeated runs raised repeated toasts for the same work. Alerts are now consolidated, and the tray remains the quiet way to see recent activity.
  • Startup registration. The engine's startup registration could end up duplicated or stale after an update, so monitoring did not begin when expected. Registration now resolves cleanly on launch and survives a re-install.
  • Duplicate file safety. Grouping could present a file as a duplicate in circumstances where keeping it was correct. Comparison now runs on chunked content and always requires confirmation before anything moves to the Recycle Bin.
  • Real-time monitoring edge cases. Certain renames and rapid write sequences left watchers behind. The engine now re-attaches and re-scans cleanly.
  • Installer reliability. Interrupted or repeated setup runs could leave a half-finished install. The NSIS package now completes or rolls back predictably.
  • Uninstall data retention. App data was not handled as documented when the program was removed. Uninstall through Settings > Apps > Installed apps now behaves as the privacy policy describes.

The same release reworked the AI workspace, added provider profiles and switching without data loss, brought Ctrl + K to the front end, and improved layout, typography, the dark theme and message bubbles. The full list is on the releases page and in the changelog.

Being watched

These behaviours are reported often as bugs and are working as designed. Understanding why each one happens usually ends the investigation before it starts.

  • The tray icon is not visible. Windows keeps new icons in the overflow area until you place them yourself. Open the hidden-icons chevron next to the clock; the menu holds Open Desktop Organizer, Organize All, Show recent activity and Quit Desktop Organizer.
  • Closing the window did not stop anything. The close button hides the interface and monitoring continues in the tray. Quitting from the tray menu is what stops the engine, which is why a file can get filed while no window is open.
  • New files do not move at once. A file waits out the stabilization delay (2 seconds by default) and, in Downloads, the completion delay (10 seconds by default) before it is eligible. That pause is the protection against filing a half-written download.
  • OneDrive folders behave oddly. Cloud-only placeholders have no local content to read, so they may be skipped, or the watcher may cause one to materialise as it inspects it. Expect a sync burst after a bulk move, and treat placeholders as out of scope.
  • Antivirus quarantines the installer. An unsigned, low-reputation executable is exactly what aggressive scanning flags. It is a false positive; verify the hash, restore from the quarantine if you wish, and follow the open issue above.
  • This site looks wrong without internet. Fonts are requested from the Google Fonts CDN, so offline the page falls back to a system font and spacing shifts. Nothing about the app depends on that connection.

Two folder types to leave alone

Do not watch a folder another application owns outright — a mail client's store, a database directory, a live video project — and do not point monitoring at a synced root you also reorganise by hand. Both produce churn that no tool, including this one, will make predictable.

How to report an issue

There is no crash reporting in the app and no telemetry, which means a report is the only way a problem becomes visible to the maintainer. Four pieces of information turn a vague complaint into something fixable.

  • Version and Windows build. Say v1.0.2 explicitly, and whether the install is per-user or managed by your IT.
  • Settings diagnostics. Open Settings and read the diagnostic state first: which folders are enabled, the two delay values, whether the engine is running, and where the app data folder sits. Copy what you see.
  • The monitoring log. Engine logs stay in the app data folder inside your Windows user profile. Quote the lines covering the minute the file should have moved, and paste text rather than attaching a whole folder.
  • Reproduction. The path, the file name pattern or extension, what you expected and what actually happened, in that order.

Report in the issue tracker, after a search for the same symptoms; a duplicate costs the same reading time as a new one. Before you paste anything, strip what you would not want public: full paths that carry a client name, document titles that identify a person, and any key. Never include your provider configuration. If a maintainer asks for more, add it in the thread rather than editing the first message, so the history stays readable.

Set expectations honestly: the project is maintained by Ahmed-Coder, free and MIT licensed, with no support contract behind it. There is no guaranteed response time and no promised fix date — the terms of use say as much — but a report with a reproduction and the relevant log lines is what moves the backlog, and the resolved list above is evidence that it does. Anything you would not want in public, including a suspected security problem, should be raised privately through the repository rather than posted as an open issue.

Good report, in short form

"v1.0.2, Windows 11, per-user install. Downloads is watched, stabilization 2 s, completion 10 s. A completed 4 GB ISO was filed into Archives about 40 seconds after the browser finished; the log shows one move entry and no error. I expected it to wait for the completion delay." That is enough to start.
